How I design interactive HTML learning experiences

This is my personally developed process for designing interactive learning experiences. What this approach tries to solve

I treat learning design and visual design as one connected system.

A lot of experience design processes are either too visual too early or too instructional in a way that ignores the actual user experience. My process tries to bridge those two worlds. I define the learning, choose the right interaction model, map the experience, shape the visuals, test clarity, build reusable components, and document the reasoning so the system can scale.

Objective

What should the learner know or do?

The goal has to be concrete enough to design around.

Action loop

What does the learner repeatedly do?

The interaction pattern should let them practice the real thinking.

Mastery evidence

How do I know they got it?

Feedback, scoring, and assessment should prove the objective was met.

◎
Phase 1 · Define the learning experience

I start with the learning—not the layout.

I define the target learner, objective, constraints, and evidence of mastery before deciding what the experience should look like.

Open / close
This first phase is where I make sure the experience has an actual reason to exist. If the goal is fuzzy here, everything downstream gets weaker.
1

Establish the learning goal

Define what students should know or be able to do by the end.

+

I define the target learner and grade level, the learning objective, academic standards, expected session length, prior knowledge, evidence of mastery, accessibility requirements, and device or browser constraints.

Example

“Students will identify three indicators of a phishing email and correctly decide how to respond.”

IncludeTarget learner, objective, standards, session length, prior knowledge, evidence of mastery, accessibility level, device/browser requirements
2

Select the experience format

Choose the interaction model that best demonstrates the learning objective.

+

I choose the format based on what kind of thinking or decision-making the learner needs to practice. The format should serve the objective—not merely make the lesson feel game-like.

Common formats

Guided simulation, branching scenario, investigation, decision challenge, puzzle, digital lab, role-playing experience, card sort, narrative adventure, build-and-test challenge.

My rule

If the format adds energy but does not reveal mastery, I rethink it.

3

Define the core experience loop

Identify what the learner repeatedly does.

+

I identify the repeated action cycle the learner moves through. That loop becomes the real backbone of the experience.

Example loops

General: Observe → Investigate → Decide → Receive feedback → Advance

Phishing lesson: Open message → Inspect clues → Mark evidence → Choose response → See consequences

Practical rule

I try to keep each screen centered on one primary task or decision. It makes the experience easier to understand and easier to test.

▦
Phase 2 · Plan the content and flow

I map the learner journey before I style it.

I define the screens, possible paths, content needs, and assessment logic before producing polished visuals.

Open / close
This phase prevents me from designing around incomplete assumptions. It is where the structure becomes visible.
4

Create the experience map

Map every screen and possible path before designing visuals.

+

I map the entry, instructions, challenges, feedback moments, optional clues, recovery paths, assessment, completion screen, and replay or next-step options. If the experience branches, I show where paths diverge and where they reconnect.

IncludeMission briefing, instructions, primary challenges, feedback, optional help, incorrect-answer recovery, assessment, completion, replay
5

Create a content inventory

List everything the experience needs before the interface hardens around placeholders.

+

I list instructions, dialogue, questions, images, characters, emails or documents, clues, feedback messages, sounds, scores, badges, and progress indicators. This keeps the interface from being built around fake content that later breaks the layout.

6

Define assessment and feedback

Determine how the experience will measure learning.

+

I define what earns points, whether students can retry, how hints affect scoring, what counts as mastery, what feedback appears after each action, and what the final results screen communicates.

Important

Feedback should explain why something was correct or incorrect. “Correct” by itself does not teach much.

✦
Phase 3 · Establish the visual direction

I start loose, then make the visual direction progressively more specific.

I gather references, build a mood board, narrow to must-have qualities, define a visual vision, and test the direction with representative mockups.

Open / close
This is the phase where I shape the visual language without letting aesthetics detach from the learning goal.
7

Collect references

Gather references for layouts, real tools, characters, color, typography, motion, and atmosphere.

+

I separate references into categories instead of throwing everything into one bucket. For realistic simulations, I collect examples from the actual interfaces learners would encounter, such as email clients, dashboards, or messaging tools.

8

Build the mood board

Use the first board as a visual hypothesis—not as the final answer.

+

I organize the references in Milanote, PureRef, or Figma. The mood board helps me define emotional tone, realism, age appropriateness, visual density, interface style, character style, color and lighting, and motion style.

Design principles I might write beside the board

“Sophisticated enough for high school students.” “Realistic interfaces with stylized narrative elements.” “One important decision per screen.” “Evidence must be visible without feeling artificially obvious.”

My fast mood-board iteration loop

I added this to the article because this is one of the biggest parts of my real process. I do not stop at “make a mood board.” I use the mood board as raw material, distill it, test it, and then feed the results back into the system.

A

Slap together a mood board

Collect anything that captures a useful quality.

+

I gather anything that captures a useful quality: believable interface fragments, lighting treatments, character styling, interesting color relationships, transitions, textures, and atmosphere. I allow contradiction at this stage because contrast helps me see the available directions.

Output

A broad, imperfect reference field.

B

Narrow to the must-haves

Use the learning goal and experience constraints as a filter.

+

I identify three to five visual qualities the design cannot lose. Those might include realistic source material, mature character styling, low clutter, discoverable evidence, or a very clear focal point.

Output

A short list of visual non-negotiables.

C

Extract a working color scheme

Convert visual inspiration into functional roles.

+

I sample the strongest color relationships and convert them into roles: page background, surfaces, primary action, selected evidence, warning, success, danger, and subdued information. I tune those colors for readability and contrast rather than copying a source palette exactly.

Output

A role-based, accessibility-aware palette.

D

Write the shorter visual vision document

Compress the board into a concise direction another person could actually use.

+

I condense the mood board into a shorter visual vision. This helps me move from visual inspiration to explicit design direction.

My one-page visual vision usually includes
  • One sentence describing what the learner should feel and do
  • Three to five must-have traits
  • An avoid list
  • How realism and stylization should balance
  • Palette roles rather than random swatches
  • The hierarchy rule for goal, action, evidence, and feedback
  • Motion rules
  • Production constraints and responsive notes
E

Mock up representative art and document the reaction

Test the direction on a demanding screen and record what works.

+

I apply the direction to one demanding, representative screen. Then I document what supports the learning, what competes for attention, what feels too young or too corporate, and what breaks when realistic content is inserted.

Keep

What immediately supports tone, clarity, or authenticity?

Change

What competes with the task or obscures interaction?

Question

What still needs learner, stakeholder, or technical validation?

Systemize

Which successful decisions can become reusable components or rules?

F

Iterate again using the mockup as inspiration

Feed the test result back into the mood board, palette, and design rules.

+

This is the part I think many visual processes miss. I use the mockup itself as new reference material. I revise the board, tighten the must-haves, refine the palette, adjust the visual vision, and then test again. Each pass should reduce ambiguity and make the system more reusable.

Output

A clearer direction with fewer unresolved choices.

9

Establish the design system

Create the rules before producing complex artwork.

+

I define the primary, secondary, and accent colors; success, warning, danger, and neutral states; type scale; spacing scale; button styles; cards and panels; icon style; focus, hover, selected, and disabled states; and basic animation behavior.

◫
Phase 4 · Design the interface

I prove clarity before I invest in polish.

I sketch, wireframe, prototype, and observe real users before committing to expensive visuals.

Open / close
10

Sketch and wireframe

Start in grayscale and make sure the screen works before style is added.

+

I establish information hierarchy, primary action, navigation, dialogue placement, clue locations, progress indicators, feedback areas, and help or accessibility controls. If the structure is weak in grayscale, color will not save it.

11

Build a low-fidelity prototype

Create clickable blocks with realistic amounts of text.

+

I test spacing, reading order, number of clicks, menu behavior, navigation clarity, character movement if applicable, decision flow, feedback timing, and smaller-screen behavior. At this stage, structure changes should still be inexpensive.

12

Conduct a clarity test

Watch users try it without your narration.

+

I observe where they look first, what they think is clickable, whether they understand the goal, where they hesitate, whether they miss information, whether feedback helps, and whether they can recover from mistakes. Clarity testing happens throughout—not only after the interface is “done.”

✧
Phase 5 · Create the visual experience

I add atmosphere without sacrificing comprehension.

Once the structure is clear, I add typography, color, lighting, interface detail, and composition in a way that still preserves readability and task clarity.

Open / close
13

Produce the high-fidelity design

Add final typography, color, illustrations, interface details, sound cues, and microinteractions.

+

I maintain a clear distinction between decorative, interactive, informational, and assessment elements. That separation helps the learner know what matters at a glance.

14

Apply composition and hierarchy rules

Use visual direction intentionally, not decoratively.

+

I place the primary objective, clue, or action where the learner is most likely to look first. I use scale, contrast, spacing, gaze direction, lighting, and leading lines to support that priority.

Visual hierarchyUse size, contrast, spacing, and restrained motion to establish what matters most.
Aspect ratio & responsivenessChoose a base viewport, but define how the interface scales, wraps, collapses, and behaves on smaller screens.
ReadabilityDefine rules for font size, line length, spacing, contrast, button size, text over images, and captions.
⌘
Phase 6 · Build and validate

I build a reusable learning system—not a collection of one-off pages.

I move from visual design into reusable HTML components, then test learning, usability, accessibility, and technical behavior.

Open / close
15

Create the HTML prototype

Build with reusable components instead of designing every lesson as a separate application.

+

I build components like mission briefings, dialogue panels, email or document viewers, evidence inspectors, multiple-choice decisions, drag-and-drop activities, hotspot scenes, hint systems, feedback panels, progress trackers, and results screens.

Technical preference

When possible, I keep lesson content separate from the interface code. A JSON-based structure makes the engine easier to reuse across multiple lessons.

16

Test the complete experience

Test learning, usability, accessibility, and technical performance.

+
LearningDoes the experience actually demonstrate mastery of the objective?
UsabilityCan students understand what to do without teacher intervention?
AccessibilityCan it be completed with keyboard navigation, screen readers, captions, and sufficient contrast?
TechnicalDoes it work across supported devices, screen sizes, and browsers without losing progress?

I also test loading time, broken interactions, keyboard focus, scoring, retries, saved state, audio controls, and accidental refreshes.

17

Pilot and improve

Use a small representative student group before treating it as final.

+

I collect completion rate, time per challenge, incorrect-answer patterns, hint usage, abandonment points, assessment results, student confidence, and student comments. Then I use those findings to determine whether problems come from the content, interface, instructions, or difficulty.

☰
Phase 7 · Package for reuse

I preserve the reasoning—not only the finished screens.

I document enough of the process that the experience can be maintained, scaled, and understood by other people later.

Open / close
18

Document the completed experience

Save the reasoning, not just the final visuals and code.

+

I save the learning brief, experience map, script and content, mood board, design system, component inventory, assessment logic, accessibility checklist, testing results, and final source files. This is what makes the process scalable across multiple lessons and designers.

Compact version

Define → Select → Map → Assess → Reference → Distill → Mock up → Prototype → Test → Style → Build → Validate → Improve

If I had to summarize the entire approach in one sentence, it would be this: I connect the learning objective, the repeated learner action, and the evidence of mastery—and then I make every visual, interaction, and technical decision support that triangle.

Final thought

My process is meant to be practical.

It is visual, but not style-first. It is instructional, but not dry. It is technical, but still rooted in how learners actually move through a screen. If you want, I can next turn this into an even more visual playbook, a slide deck, or a design-system style lesson template.
